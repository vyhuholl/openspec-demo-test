# Демо: OpenSpec против чистого вайбкодинга

Сравнение двух подходов к реализации одной и той же нетривиальной фичи в одном и том же репозитории, одним и тем же агентом, по одному и тому же промпту. Агент — Claude Code, модель `glm-5.3`, medium effort. Берём сервис бронирования переговорок и пытаемся туда добавить повторяющиеся брони дважды — «голым» вайбкодингом и через OpenSpec.

Этот лист скрыт от агента до разбора. По нему ведущий отвечает на вопросы агента, по нему же написаны внешние приёмочные тесты.

Основной репозиторий https://github.com/vyhuholl/openspec-demo

Ветки:

Название | Содержимое
--- | ----
`master` | базовый сервис бронирования
`spec` | он же + настроенный OpenSpec и конституция проекта. В конституции есть карта критичности требований.

От `master` пробуем реализовать фичу чистым вайбкодингом, прогоняем приёмочные тесты, смотрим на результат. Затем — то же самое через OpenSpec от ветки `spec`.

## Промпт

Один и тот же для обоих веток. В ветке `spec` подаётся через `/opsx:explore`.

```
Добавь повторяющиеся брони (серии): ежедневно, еженедельно, по выбранным дням недели.
При создании серии сразу создаются все отдельные брони на указанный период.

POST /series
{
  "room":   "green",
  "start":  "2027-11-01T09:00:00Z",
  "end":    "2027-11-01T10:00:00Z",
  "repeat": "daily" | "weekly",
  "days":   ["mon", "wed", "fri"],
  "until":  "2027-12-31"
}
  start/end — первое вхождение, в том же формате, что в POST /bookings.
  days — только для weekly, необязательное; значения mon, tue, wed, thu, fri, sat, sun.
  until — дата окончания серии, YYYY-MM-DD.

201: {"id": "<id серии>", "bookings": [<созданные брони в формате ответа POST /bookings, по возрастанию start>]}
Остальные коды ответов — по сложившимся в сервисе соглашениям.
Брони серии видны в GET /bookings как обычные.

Существующие эндпоинты не меняются, новых обязательных полей в запросах нет.
Отмену и редактирование серий не добавляй.
Покрой тестами, как принято в репозитории.
Готово, когда make ai-check зелёный.
```

## Ответы на вопросы агента

- Отвечать на вопросы агента только по этому листу и одинаково в обеих ветках. Vibe-агент тоже может спросить — отвечать ему так же.
- Отвечать на заданный вопрос, не выдавая соседние пункты: спросили про until — не рассказывать про таймзону.
- Вопроса нет в листе → «На ваше усмотрение, зафиксируйте как допущение». Приёмка такие места не проверяет.
- Агент предлагает варианты и просит выбрать → выбрать тот, что совпадает с листом; если ни один не совпадает — ответить по листу своими словами.
- Ничего не сообщать без вопроса.

**Q1. Таймзона.** Все переговорки в одном офисе, в Берлине. «Каждый день в 10:00» — это 10:00 по Берлину круглый год: после перевода часов время в UTC сдвигается на час. Дни недели и даты (days, until, «день первого вхождения») тоже берлинские. В API время остаётся в UTC, полей в запросе не добавляем, таймзону не настраиваем.

*(Почему Берлин, а не Москва — чтобы проверить перевод часов.)*

**Q2. until.** Включительно: вхождение в день until создаётся. until равен дате первого вхождения — серия из одной брони, это нормально. until раньше даты первого вхождения — 400.

**Q3. Горизонт.** until — не позже чем через календарный год от даты первого вхождения: с 1 ноября 2027 можно до 1 ноября 2028 включительно, 2 ноября 2028 — уже 400.

**Q4. Конфликт.** Если хоть одно вхождение пересекается с существующей бронью — 409 на всю серию, не создаётся ни одной брони. Касание (конец одной = начало другой) — не конфликт, как у одиночных броней.

**Q5. Дни недели.** weekly без days — по дню недели первого вхождения. Первое вхождение — всегда start, поэтому день start обязан входить в days, иначе 400. Неизвестный день, days при daily, неизвестный repeat — 400.

**Q6. Самопересечение.** Вхождения одной серии не должны пересекаться друг с другом (например, daily длительностью больше суток) — 400, ничего не создаётся.

**Q7. Одновременные запросы.** Две брони в одной комнате не пересекаются никогда, в том числе при одновременных запросах. Серия создаётся целиком или не создаётся вовсе.

## Запуск приёмочных тестов

Из корня этого репозитория:

```bash
./judge.sh <путь к основному репозиторию>
```

Скрипт собирает `cmd/booking`, временно кладёт тесты в `<repo>/acceptance/` и после прогона удаляет.

## Что проверяют приёмочные тесты

Типы тестов: **инвариант** — те, где правильный ответ однозначен без дополнительных уточнений, **спросить** — те, где агент должен задать вопрос. Ошибка в тесте первого типа значит, что фича просто не работает, в тесте второго типа — что агент не уточнил требования и реализовал не то поведение, которое нам нужно было.

Курсивом выделены тесты, на которых вайбкодинг-решение стабильно ломается.

| Тест | Пункт | Тип | Типовая ошибка, которую ловит |
|---|---|---|---|
| TestSeries_Daily_CreatedAndListed | промпт | контракт | время не в UTC, нет сортировки, брони не видны в GET |
| TestSeries_Until | A2 | выбор | until исключительно или сравнение с полуночью UTC |
| TestSeries_Horizon / exactly_one_year, one_year_and_one_day | A3 | выбор | лимита нет; лимит «365 дней» (2028 високосный) |
| TestSeries_Horizon / hundred_years_daily | A3 | инвариант | лимита нет: «ежедневно на 100 лет» — 36 500 броней |
| TestSeries_Conflict_WholeSeriesRejected | A4 | выбор | конфликтное вхождение пропускается |
| TestSeries_TouchingExisting | A4 / B2 | выбор | касание считается конфликтом (стадия 1) или буфер обходит серии (стадия 2) |
| TestSeries_Weekly / selected_days | A5 | инвариант | ошибка в разворачивании дней |
| TestSeries_Weekly / days_omitted…, start_weekday_not_in_days | A5 | выбор | первым вхождением молча становится start |
| TestSeries_InvalidRequest | A5, соглашения | контракт | мягкая валидация |
| TestSeries_SelfOverlap / no_double_booking | A6 | инвариант | проверка вхождений только против уже существующих броней — двойная бронь |
| TestSeries_SelfOverlap / status_400 | A6 | выбор | 409 вместо 400 |
| TestSeries_DST | A1 | спросить | повторение в UTC: после перевода часов встреча уезжает на час |
| TestSeries_Concurrent_InvariantHolds | A7 | инвариант | проверка и вставка под разными захватами блокировки; гонка данных (бинарник собран с -race) |
| TestBase_SingleBooking | база / B2 | регрессия | сломано старое поведение одиночных броней |
| TestBuffer_Single | B1 | выбор | `>` вместо `>=`; буфер только с одной стороны |
| TestBuffer_Series_ViolationRejectsWholeSeries | B3 | спросить | агент выполнил «пропусти» из промпта |
| TestBuffer_Series_ExactlyTenMinutes | B1, B3 | выбор | граница в серии |
| TestBuffer_SingleNextToSeriesOccurrence | B3 | инвариант | буфер не учитывает брони серий |

## Выводы

* Там, где агент задал вопрос во время `/opsx:explore`, код правильный в 100% случаев.
* Каждая ошибка в spec-ветке — незаданный вопрос, и он виден в `proposal.md` как допущение ещё до кода;
* При чистом вайбкодинге агент те же решения принимает молча, их негде увидеть. Как результат — молча получается немного не совсем то поведение, которое нам нужно было.
