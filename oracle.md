# openspec-demo

Этот лист скрыт от агента до разбора. По нему ведущий отвечает на вопросы агента, по нему же написаны внешние приёмочные тесты.

Репозиторий https://github.com/vyhuholl/openspec-demo

Ветки:

Название | Содержимое
--- | ----
`master` | базовый сервис бронирования
`vibe-change-1` | совпадает с `master`
`spec-change-1` | `master` + настроенный OpenSpec и конституция проекта
`vibe-change-2` | change 1 уже реализован без OpenSpec
`spec-change-2` | change 1 уже реализован с OpenSpec

Клонируем только нужную нам ветку:

```bash
git clone https://github.com/vyhuholl/openspec-demo.git single-branch -b
```

## Правила для ведущего

- Промпты одинаковые для обеих веток. В `spec-*` подаются через `/opsx:explore`, в `vibe-*` — как есть. Каждый change — в новой сессии Claude Code.
- Отвечать на вопросы агента только по этому листу и одинаково в обеих ветках. Vibe-агент тоже может спросить — отвечать ему так же.
- Отвечать на заданный вопрос, не выдавая соседние пункты: спросили про until — не рассказывать про таймзону.
- Вопроса нет в листе → «На ваше усмотрение, зафиксируйте как допущение». Приёмка такие места не проверяет.
- Агент предлагает варианты и просит выбрать → выбрать тот, что совпадает с листом; если ни один не совпадает — ответить по листу своими словами.
- Ничего не сообщать без вопроса.

## Change 1 — серии

Промпт:

```
Добавь повторяющиеся брони (серии): ежедневно, еженедельно, по выбранным дням недели.
При создании серии сразу создаются все отдельные брони на указанный период.

POST /series
{
  "room":   "green",
  "start":  "2027-11-01T09:00:00Z",
  "end":    "2027-11-01T10:00:00Z",
  "repeat": "daily" | "weekly",
  "days":   ["mon", "wed", "fri"],
  "until":  "2027-12-31"
}
  start/end — первое вхождение, в том же формате, что в POST /bookings.
  days — только для weekly, необязательное; значения mon, tue, wed, thu, fri, sat, sun.
  until — дата окончания серии, YYYY-MM-DD.

201: {"id": "<id серии>", "bookings": [<созданные брони в формате ответа POST /bookings, по возрастанию start>]}
Остальные коды ответов — по сложившимся в сервисе соглашениям.
Брони серии видны в GET /bookings как обычные.

Существующие эндпоинты не меняются, новых обязательных полей в запросах нет.
Отмену и редактирование серий не добавляй.
Покрой тестами, как принято в репозитории.
Готово, когда make ai-check зелёный.
```

### Ответы на вопросы

**A1. Таймзона.** Все переговорки в одном офисе, в Берлине. «Каждый день в 10:00» — это 10:00 по Берлину круглый год: после перевода часов время в UTC сдвигается на час. Дни недели и даты (days, until, «день первого вхождения») тоже берлинские. В API время остаётся в UTC, полей в запросе не добавляем, таймзону не настраиваем.

*(Почему Берлин — чтобы проверить перевод часов.)*

**A2. until.** Включительно: вхождение в день until создаётся. until равен дате первого вхождения — серия из одной брони, это нормально. until раньше даты первого вхождения — 400.

**A3. Горизонт.** until — не позже чем через календарный год от даты первого вхождения: с 1 ноября 2027 можно до 1 ноября 2028 включительно, 2 ноября 2028 — уже 400.

**A4. Конфликт.** Если хоть одно вхождение пересекается с существующей бронью — 409 на всю серию, не создаётся ни одной брони. Касание (конец одной = начало другой) — не конфликт, как у одиночных броней.

**A5. Дни недели.** weekly без days — по дню недели первого вхождения. Первое вхождение — всегда start, поэтому день start обязан входить в days, иначе 400. Пустой days, неизвестный день, days при daily, неизвестный repeat — 400.

**A6. Самопересечение.** Вхождения одной серии не должны пересекаться друг с другом (например, daily длительностью больше суток) — 400, ничего не создаётся.

**A7. Одновременные запросы.** Две брони в одной комнате не пересекаются никогда, в том числе при одновременных запросах. Серия создаётся целиком или не создаётся вовсе.

## Change 2 — буфер

Промпт:

```
Между бронями одной комнаты нужен перерыв 10 минут на уборку.
Если при создании серии какое-то вхождение не проходит по буферу — пропусти его, как у нас принято с конфликтами.
Контракт API не меняется.
Покрой тестами, как принято в репозитории.
Готово, когда make ai-check зелёный.
```

*(Вторая строка намеренно противоречит тому, как работает фича из change 1 — моделируем ситуацию «заказчик перепутал» и смотрим, отловит ли агент противоречие.)*

### Ответы на вопросы

**B1. Размер.** Между концом одной брони и началом следующей в той же комнате — не меньше 10 минут. Ровно 10 — можно, 9 — 409. Действует в обе стороны: и перед существующей бронью, и после неё. Другие комнаты не влияют. 10 минут фиксированы, настраивать не нужно.

**B2. Касание.** Теперь конфликт (409). Это осознанное изменение прежнего правила.

**B3. Серии.** Буфер действует на всё, что создаёт брони: одиночные и серии. Если агент заметит противоречие с фразой «пропусти, как у нас принято» (спросит сам или сошлётся на спеку/код): «Я перепутал. Как с конфликтами: вхождение не проходит по буферу — 409 на всю серию, ничего не создаётся».

## Запуск приёмочных тестов

В корне основного репозитория, после изменений агента:
```bash
make run
```
Затем в папке с тестами и `judge.sh`:
```bash
./judge.sh <путь к рабочей копии ветки> <1|2>
```

- `1` — после change 1, `2` — после change 2.
Скрипт кладёт тесты в `<repo>/acceptance/`, собирает `cmd/booking` с `-race`, поднимает сервис на свободном порту, после прогона удаляет `acceptance/`. Затем показывает удалённые строки в тестах, существовавших на base: так видно, переписал ли агент старые ожидания. На стадии 2 правка ожиданий про касание законна (B2), остальное — повод для разбора.

## Что проверяет приёмка

Типы: **инвариант** — правильный ответ однозначен без заказчика; **спросить** — однозначен, но узнать можно только вопросом; **выбор** — решение заказчика, могло быть другим; **контракт** — LOW.

| Тест | Пункт | Тип | Типовая ошибка, которую ловит |
|---|---|---|---|
| TestSeries_Daily_CreatedAndListed | промпт | контракт | время не в UTC, нет сортировки, брони не видны в GET |
| TestSeries_Until | O2 | выбор | until исключительно или сравнение с полуночью UTC |
| TestSeries_Horizon / exactly_one_year, one_year_and_one_day | O3 | выбор | лимита нет; лимит «365 дней» (2028 високосный) |
| TestSeries_Horizon / hundred_years_daily | O3 | инвариант | лимита нет: «ежедневно на 100 лет» — 36 500 броней |
| TestSeries_Conflict_WholeSeriesRejected | O4 | выбор | конфликтное вхождение пропускается |
| TestSeries_TouchingExisting | O4 / B2 | выбор | касание считается конфликтом (стадия 1) или буфер обходит серии (стадия 2) |
| TestSeries_Weekly / selected_days | O5 | инвариант | ошибка в разворачивании дней |
| TestSeries_Weekly / days_omitted…, start_weekday_not_in_days | O5 | выбор | первым вхождением молча становится start |
| TestSeries_InvalidRequest | O5, соглашения | контракт | мягкая валидация |
| TestSeries_SelfOverlap / no_double_booking | O6 | инвариант | проверка вхождений только против уже существующих броней — двойная бронь |
| TestSeries_SelfOverlap / status_400 | O6 | выбор | 409 вместо 400 |
| TestSeries_DST | O1 | спросить | повторение в UTC: после перевода часов встреча уезжает на час |
| TestSeries_Concurrent_InvariantHolds | O7 | инвариант | проверка и вставка под разными захватами блокировки; гонка данных (бинарник собран с -race) |
| TestBase_SingleBooking | база / B2 | регрессия | сломано старое поведение одиночных броней |
| TestBuffer_Single | B1 | выбор | `>` вместо `>=`; буфер только с одной стороны |
| TestBuffer_Series_ViolationRejectsWholeSeries | B3 | спросить | агент выполнил «пропусти» из промпта |
| TestBuffer_Series_ExactlyTenMinutes | B1, B3 | выбор | граница в серии |
| TestBuffer_SingleNextToSeriesOccurrence | B3 | инвариант | буфер не учитывает брони серий |
